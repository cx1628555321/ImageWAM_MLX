# 优化方向重新评估（2026-11-05）

本次为代码、既有实验及官方资料复核，没有运行新性能基准，没有修改生产推理或权重。结论：先补齐真实执行时间线和跨进程复现方法，再优化视觉前缀与动作分支；暂缓继续广泛扫描融合、分块和提交参数。

## 1. 固定目标与可信基线

开发环境：M5 Pro，15 CPU / 16 GPU，24 GiB统一内存，macOS27.2，Python3.12.13，MLX0.32.4。2026-11-05再次只读检查：开发目录为 `/Library/Developer/CommandLineTools`，`xcrun --find xctrace` 仍失败。尚不能声称已获得GPU内核级时间线。

目标：RoboTwin三图在线编码，动态文本，10步动作去噪，无跨请求文本/图像/KV特征缓存，从已解码输入到CPU反归一化动作返回。加载、磁盘读图和输出落盘另计；加载暂不优化。静态权重预打包和编译图复用不等于缓存请求特征。

|证据|结果|可以得出的结论|
|---|---|---|
|device_layout正式CLI，默认两个进程、200次|均值194.468 ms，P95 196.212 ms|当前保留实现的一次正式测量，不能承诺每次部署都达到该值|
|action_condition独立worker，默认两个进程、120次|均值200.814 ms，P95 203.492 ms|不同流程/时段；不能跨轮相减归因于代码|
|device_nax同轮8进程完整记录|201.544 → 198.652 ms|已采纳权重直读/K片段展开，均值收益约2.892 ms；P95未改善|
|双SIMD64行正式CLI|194.944 ms，P95 200.493 ms|局部prefill快约3.466 ms，整网未通过，保留显式实验|
|每请求集中时间调制|配对快0.219–0.332 ms，独立进程慢0.231 ms|未采纳，没有可确认的部署收益|

正式speed仍为四SIMD直读INT8视觉路径、W1动作自适应Split-K、功能式KV工作区、CPU预处理与GPU文本重叠。accuracy仍为默认profile，speed需要显式选择。安全实验开关不等于生产默认。

“与speed逐值一致”仅保证相对当前量化speed未新增误差，不证明相对PyTorch无损，也不代表机器人闭环成功率。错误NAX布局曾测到188 ms，但38层INT32结果全部不一致，该数字无效。

## 2. 现有计时揭示了什么、还缺什么

正式默认的同步模块诊断：文本27.575 ms、VAE 27.979 ms、视觉前缀79.381 ms、动作62.711 ms；预处理2.401 ms。优先审视视觉前缀和动作合理，但这些不是正常请求中的互斥时间片，不能相加当作端到端或GPU占用率。

`runtime.py:predict` 的profile分支在模块前后同步；正常路径先 `async_eval(hidden)`，让GPU文本与CPU预处理重叠，VAE/prefill继续通过动作依赖执行，最终转NumPy才返回CPU结果。profile模式先完成文本，改变了正常重叠关系。因此“模块快了，整网没快”不一定矛盾，也不能直接归因于后台负载。

以往还观察到单请求进程CPU时间约38 ms与100 ms两种状态。该值是各线程CPU时间之和，不能解释成主线程阻塞了100 ms，更不能直接从194 ms扣除。现有样本未证明频率、内存带宽、CPU调度或其他服务哪项是根因。

MLX延迟执行使Python构图时间与GPU执行时间不同；频繁求值和过大图都可能有成本，不能据此推导“一次编译整网一定更快”。见[MLX求值说明](https://ml-explore.github.io/mlx/build/html/usage/lazy_evaluation.html)。

## 3. 优先级P0：测出真实关键路径

交付三份小规模记录：一次正常完整请求的时间线、真实输入的一次prefill内核明细、一个真实动作step内核明细。先预热、排除加载/JIT；分段捕获用于定位，完整请求用于验证依赖与重叠。不要再次盲目捕获大量迭代生成十几GiB记录。

记录CPU构图/编码/提交、GPU实际运行与空闲间隙、command buffer边界、逐内核耗时与调用数、可用的带宽/占用计数、分配/复制。硬件计数器是否可用以工具实测为准。CPU需要线程级运行时间；栈里等待出现次数不等于CPU成本。

MLX支持 `MTL_CAPTURE_ENABLED=1` 和 `mx.metal.start_capture/stop_capture`，捕获可在Xcode查看与重放，见[官方Metal调试说明](https://ml-explore.github.io/mlx/build/html/dev/metal_debugger.html)。当前缺少完整分析工具链；下一阶段需先验证兼容工具能打开并分析小记录。捕获成功不等于分析成功，重放耗时也不能替代未插桩端到端。

如果暂时不能取得完整时间线，可以继续真实张量微测、CPU线程诊断与shape统计，但只报告局部现象，不宣布GPU带宽瓶颈或新的整网收益。安装/切换工具链和生产推理环境分开管理。

判断分流：

- GPU有明显提交间隙且CPU编码占关键路径：进入图生命周期、原生调用边界和提交优化。
- GPU连续运行且少数矩阵内核占大头：进入对应shape的布局/分块优化。
- 实测复制或中间张量读写显著：进入KV所有权、布局和中间结果压缩/融合。
- 只有跨进程慢状态，局部GPU核不变：先解释运行状态，不继续堆叠内核参数。

## 4. 优先级P1：视觉前缀，优化真实热点shape

现状：38个适用线性投影使用W4派生的预展开INT8权重，在线INT8激活、INT32累加、BF16输出。整块权重展开在加载阶段完成；不能把当前耗时笼统归为每次反量化。

下一步统计每层M/N/K、调用次数、量化/布局变换、矩阵乘、attention、后处理各自GPU耗时。按总耗时排序，不以单个孤立GEMM的最大加速比选方案。

对应方案：

1. 若直读权重效率或占用受限，对最热的少数shape进行分派；四SIMD作回退。双SIMD64行已有局部正证据，但必须先解释跨进程失效，再尝试按层启用，不能全局替换。
2. 若量化/重排读写显著，检查一个源激活是否被多个消费者重复量化。仅在量化尺度、分组、舍入、布局完全相同时复用单次请求内部结果；不同scale不能共享。已有concat/gate融合不重复包装成新成果。
3. 若attention占比突出，针对实际序列长度研究内存访问和mask布局；不再全局开启已测无收益的force_fused。

每个候选同时验证量化码/scale、INT32累加、BF16输出和整网动作。矩阵片段尺寸必须满足实际native布局；不能用最终动作误差较小掩盖内部错误。

## 5. 优先级P2：动作分支的重复开销与中间流量

`workspace.py`每步5个double block加20个single block，因此10步在代码层面有250次attention、500次KV slice_update表达式。它们不等于500次全量物理复制：MLX可能复用可捐赠缓冲区，必须测真实执行。

`action_kernel.py`明确有两段：Split-K产生 `[S,M,N]` FP32 partial，再由独立归并内核做求和、bias、gate与残差。partial的逻辑写入加读取约为 `8*S*M*N` 字节/调用（不等于DRAM实际流量）；S来自并行度目标512的启发式，未必对每个shape最优。

优先验证两项：

- 按真实shape记录S、矩阵核/归并核耗时和partial总量。若归并/中间存取占比高，评估降低S、按shape选择S，或仅对合适shape不Split-K。减少S可能降低GPU占用，必须测两端，不能单看归并变快。保留现有W1打包计算，不在每次前向展开完整浮点权重。
- 用真实请求确认KV是否发生大块复制、旧引用在哪里延长生命周期。只有复制确实落在关键路径才改所有权或数据结构；此前固定prefix/双段KV/打包重写已失败，不直接重做。不能用裸指针原地写破坏MLX依赖和别名语义。

如果时间线显示大量小核之间的提交空隙，再评估原生MLX/C++调用边界或更有针对性的合图；这属于有证据后的高成本路线，不先把Python整体重写。10个去噪step及block间有真数据依赖，不能当作独立任务并行。

## 6. 优先级P3与暂缓方向

VAE与文本各约28 ms，不是没有空间；先等待P0决定。只在出现显著热点后考虑VAE卷积布局或文本投影shape优化。已失败的VAE非对称padding、归一化融合、全局QKV合并不继续无差别组合。

暂缓：全局tile/swizzle扫参、QoS/command buffer阈值扫参、强制融合attention、每请求时间调制重排、每2/5步提交、双GPU流。已有结果足以降低优先级；不代表数学上永远不可能，只要求新的时间线证据后再重开。

继续降低激活位宽、减少步数、蒸馏、token裁剪、跨请求缓存属于另一个精度/语义取舍方向，不混入本轮10步无缓存一致性优化。多请求流水线可提高吞吐，也不能包装成单请求延迟改善。

## 7. 统一实验与发布门槛

1. 冻结源码、权重、配置、输入、噪声、启动命令和环境摘要；accuracy与speed比较分开。保留既有golden输出。
2. 先做少量基线进程估计跨进程方差，再为基线/候选各运行至少6个独立进程、随机平衡顺序；每进程独立加载、预热30次、稳态100次。若方差大则增加独立进程数，不能仅增加同进程请求数制造置信度。
3. 同进程随机配对只作筛选。正式统计保留全部进程，报告各进程均值、总体均值/P50/P95和按进程分组的区间；不能把连续请求都当独立样本。慢状态单列诊断，但不得删掉后只报最快值。
4. 未插桩性能、同步模块profile、中间trace分别运行。完整请求边界必须等到CPU动作可用，防止只测异步提交。
5. 正确性：既有51组回归；39/189-token及RoboTwin实际token长度分布补足的短/中/长输入；H1/H16/H64；三相机/状态扰动；十步动作trace。现有速度数字只覆盖标准39-token/H16，不外推所有长度。文本不得截断或固定到一个长度。
6. 新优化候选的工程推广目标为跨进程平均改善至少约2 ms或1%（以较严格者为准），且无可复现P95回退、无新增数值差异或非有限值。该阈值是后续筛选标准，不是预测收益，也不追溯否定已有经验证的小优化。
7. 同一假设最多先做2–3个有依据的候选；若只有微测收益、未进入关键路径，或独立复测不成立，则记录并停止扩展。任何整数内核正确性失败立即淘汰。

## 8. 收益预期与执行顺序

只作量级估算：如果视觉前缀实际关键路径能缩短20%，局部约节省16 ms；动作缩短20%约13 ms。它们不是测得收益，重叠、提交和状态变化可能使端到端节省更小。当前没有证据承诺从194–201 ms直接降到100 ms。

执行顺序：小型真实GPU/CPU时间线与统计协议 → 视觉热点shape/重复量化审计 → 动作Split-K流量与KV复制审计 → 少量候选实现 → 动态输入/逐层正确性 → 独立正式CLI复核 → 仅推广通过门槛者。
