# 当前 speed 路径优化审查（2026-11-05）

本轮为源码及既有实验分析，没有新增性能实测，没有修改生产推理。已通过 SHA256 确认远端 runtime.py、workspace.py、quantized.py、action_kernel.py 与本地副本一致。远端项目为 `/Users/qklj/work/cx/ImageWAM_MLX`。

## 实际基线与口径

最新独立进程复核的正式 speed 均值为 198.857681 ms，P95 为 201.320115 ms，两个进程共 200 个样本；见 README_GRAPH_DISPATCH_20261105.md。这不是本轮新测结果，也不是所有文本长度的保证值。

近轮同步诊断中，视觉 prefill 约 82–85 ms、动作十步约 62–63 ms、图像编码约 28 ms、文本编码约 28 ms。同步会改变 CPU/GPU 重叠，模块时间不能直接相加代替在线端到端耗时。

默认 Qwen 是 BF16 前 27 层；`SPEED_OPTIONS['qwen_fused']=False`，不能把 speed_qwen.py 中的合并投影当成已启用功能。视觉 38 个线性层使用预展开 INT8 权重和动态 INT8 激活，其余视觉计算保留浮点；动作符合条件的线性层使用 W1/BF16 与自适应 Split-K。默认不是全网整数计算。

## 按优先级推进

### 0. 先解释独立进程慢态

最近 xonly/every5 提交实验同进程约省 0.45–0.54 ms，独立进程反而分别慢约 8.49/11.37 ms；慢态进程 CPU 时间约 100 ms，正常约 38 ms。CPU 时间为进程各线程累计值，不是主线程时间。QoS 调整没有解决问题，现有 sample 栈不能给出 GPU 时间线或唯一原因。

方案：以原生 CLI 为唯一部署入口，保存每进程 MLX 配置、形状、内存/缺页、CPU 时间及启动顺序；随机交错多轮独立进程复核。用单独诊断运行观察 Metal 提交、GPU 空闲和缓冲分配，必要时配置完整 Xcode/Instruments；正式计时关闭采样和模块同步。首先区分 CPU 构图/提交、内存管理和 GPU 内核执行，不预先认定是大小核或热降频。

### 1. 视觉 INT8 的尾块专用调度

位置：imagewam_mlx/prepacked_visual.py 的 kernel 和 linear；融合入口 split_quant_visual.py、gate_quant_visual.py 需要使用相同派发规则。

当前 BM=64。三图产生 288 个图像 token，再加状态 token 和实际文本，39-token 样本 M=328，需要 6 个行块，最后仅 8 行有效；328/384=85.4% 是行槽利用率，不是硬件利用率或可实现加速比。RoboTwin 已扫描文本 31–79，对应 M=320–368，尾块情况随输入改变。

方案：保留完整块的既有内核，为最后不足 64 行的块开发较小 BM/线程布局；比较一次统一派发和额外尾块派发。需配套修改激活量化的打包寻址，不能仅改 BM 常量。按真实 M 派发，不截断、不固定文本长度。

风险：新增 dispatch、较差矩阵片段利用率可能抵消少算的收益。先测 linear1/linear2 的完整输入，再测正式端到端。以同权重、同累加顺序逐值一致为目标。已有 BN128 试验不等于该行尾块方案已验证。

### 2. 视觉权重供给的软件流水

同一内核每个 BK=64 循环先等待、加载权重到 threadgroup，再等待并执行矩阵乘。K=3072/12288 分别经历 48/192 个循环。这里存在可分析的数据供给和同步成本，但仅看源代码不能证明它是主要 GPU 瓶颈。

方案：先用计数器或时间线验证，再试双缓冲 threadgroup 权重块、交错下一块读取与当前块运算；保持整数累加及最终缩放顺序。现有单缓冲约 5 KiB，双缓冲约 10 KiB，可能降低驻留率。不要直接删同步，也不要重复已失败的 device 直接读取方案。优先单独验证两种 GEMM 形状，不全网一刀切。

### 3. 动作 KV 更新：先证实复制，再设计存储

位置：workspace.py。每步 25 层，每层两次 slice_update，十步为 500 次逻辑更新。前缀不变，只有动作槽更新；但 MLX 可能复用缓冲，逻辑操作数不能当成物理复制次数。

以 P=328、24 头、128 维、BF16 为例，全部层 K/V 前缀大小约 96.1 MiB；如果每步完整复制一遍，仅复制内容约 961 MiB/请求，读写流量还需分别计算。这只是条件上界估算，不是测量。

方案：先确认实际分配/复制成本。仅在证实有显著复制后，考虑拥有明确生命周期的请求内缓冲，或只读前缀与短动作尾的专用注意力接口。原来的分段注意力已试过且未证明整体收益，不应原样再试；不跨层共享不同 K/V，不直接对 MLX 函数式输入做未声明的原地修改。

### 4. 大幅提速需要单独的业务/算法模式

* 同一指令连续控制时，可选缓存 Qwen 特征，键包含完整 token、模型/模板/分词器版本及 dtype；设置容量和失效规则。图像和状态仍每帧计算，不能缓存完整 visual KV。报告命中与未命中两套端到端结果，不将命中结果替代当前无缓存基线。约 28 ms 的文本诊断时间不等于净节省时间，原有 CPU/GPU 重叠会变化。
* 精度让步模式可扫描 10/8/6/4 步，必要时训练少步蒸馏模型。按约 62.5 ms 的动作诊断时间线性估算，10→6 步的算术预算约省 25 ms，仅用于规划；实际端到端与控制成功率必须重新测。不能宣称动作输出不受影响。

## 暂不重复投入的方向

全网统一低比特、盲目增加融合、双 GPU stream、无条件加宽 BN、提高 Split-K 并行度、减少 async_eval 次数、直接设备读取权重、改变 QoS 均不能仅凭理论并入默认。历史候选已有失败或不稳定证据。Qwen 合并投影、RoPE 融合、VAE GN 变体也不是未经尝试的新方案。

## 合入门槛

1. 同进程随机配对筛选后，必须通过多轮独立进程的原生入口复核，保存全部样本及均值/P50/P95，不删慢态样本。
2. 使用现有 51 组真实输入覆盖，补充动态文本、H=1/8/16/64、不同步数和长度切换。严格等价优化比较 normalized/action 逐值结果；误差型方案另报相对 speed 与 accuracy 的误差。
3. 量化 speed 的数值本来就不同于 PyTorch/accuracy。相对 speed 一致不代表原模型精度无损，少步等算法改变还需 RoboTwin 闭环成功率。
4. 保留模型加载、首次推理与稳态记录；本轮优先优化稳态，不以加载优化替代请求延迟收益。

建议实施顺序：独立进程慢态定位 → 视觉尾块 → 有性能证据支撑的软件流水 → KV 复制审计。业务缓存和少步推理作为独立模式并列评估，不改变当前基线定义。
