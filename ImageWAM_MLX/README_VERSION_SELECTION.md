## 推荐固化版本：native-w4-zip252-20261109

选用 **native-w4＋merge252**。400组端到端配对中，均值155.61→148.00ms（降低4.89%，节省时间95%区间4.30～10.87ms），P50为141.28ms，P95由187.15降至182.53ms。ZIP净新增开销0.76～0.87ms已包含在端到端中。360组动作对照的归一化RMSE为0.003649，最大绝对偏差0.144531；该方案160次跨进程重复输出全部逐位一致（五个配置合计800次）。

选择理由：merge252与prune252总体偏差接近，本轮merge252的均值和P95均改善；prune252平均节省略多但P95变差，未证明其稳定优于merge252。prune216的总体偏差更大；late_align32虽偏差最小，但提速区间跨0。因此选择merge252是当前数据下的工程折中，不宣称它在所有输入上最优。

固定配置：MLX `0.32.5.dev20261106`，speed＋all_int8前缀，native W4动作专家；第5个双流块后由288压缩至252个视觉token（240重要＋12上下文代表，三视角配额168/42/42）；保留原位置编码；10轮去噪，16×14动作输出；文本缓存1条；VAE asymmetric关闭；MLX默认allocator策略，算子批量参数256。输入图像、状态和前缀每次重算。性能数字适用于文本缓存命中，不包含加载和文件I/O。

固定入口只接收输入、文本、噪声/种子、预热次数和输出路径，拒绝覆盖步数、压缩方案及模型配置。启动时核对源码SHA256，`run.json.frozen_version`记录版本ID与manifest哈希。manifest位于 `versions/native-w4-zip252-20261109.json`。权重与assets沿用项目现有文件；此清单锁定配置和源码，不包含或校验大权重文件，复制到其他环境时仍需确保使用相同模型资产。

## 如何理解性能和精度

- 所有行均为三图输入、H16、14维动作、10步。除accuracy外，性能是文本缓存命中路径，图片和状态每次重算。端到端不含加载、磁盘读取、保存或仿真。新运行时版本正式测量为每进程10次预热、50次计时并交叉复测；accuracy的281.650ms是历史8次预热、100次测量。
- 不同批次受系统负载/调度波动影响，不能用两行差值声称某项优化净收益。W1后续窗口约145–150ms；action-bf16的同期W1为150.171ms。CLI的run.json.request_ms是单次请求，不是表中多次均值。
- 多样本精度统计覆盖真实36–51 token指令，输入与噪声完全一致。此前31–79 token长度压力测试是另一套；不要把它当成本表的独立真实场景。
- accuracy误差为0仅因为它是参照，不代表没有模型误差。action-bf16平均误差比W4低，但最大单元素差略高，不能保证每个样本都优于W4。
- 示范动作误差按当前帧起连续16步计算，包含12个关节与2个夹爪；量纲混合，只用于相同定义下的对照。分维统计见完整报告。
- 数据元信息标记train，本次未核验训练留出划分。**这是离线数值/示范误差验证，不是独立测试集泛化结论，也没有完成RoboTwin闭环成功率验证。** 不把RMSE换算成“准确率百分比”。

## 换自己的输入与取回输出

`inputs.npz`需要三路uint8、HWC、RGB图像：`cam_high`、`cam_left_wrist`、`cam_right_wrist`，以及float32的14维`state`。当前样本图像为480×640。`prompt.txt`为完整模型提示词；也可用`--instruction '任务描述'`替换`--prompt-file`，入口会添加训练提示前缀，不要同时传两者。文本没有固定为本表某个长度，仍受模型上下文上限约束。

### 压缩位置、维度与模块成本

维度采用NHWC，`T`为实际文本长度。原始链路是：

```text
三视角缩放拼图                 [1, 288, 256, 3]
VAE                            [1, 36, 32, 32]
2×2 latent打包                  [1, 18, 16, 128]
展平视觉token                  [1, 288, 128]
img_in                         [1, 288, 3072]
文本T个＋状态1个，经txt_in      [1, T+1, 3072]
前缀长度                       N = T+1+288
每层K、V（各自）               [1, 24, N, 128]
动作专家：16个查询、10轮去噪    [1, 16, 14]
```

`merge252` / `prune252`在第5个双流块完成后压缩视觉特征：`[1,288,3072] → [1,252,3072]`。前5层KV仍为完整N；后20层KV长度为`T+1+252`。例如T=42时，**早期层331、后续层295**，不能把整网都标成295。动作专家仍计算16个查询，只是对应层可读的前缀KV减少。

`late_align32`在第15个前缀块后，仅从主视角移除`(288+T+1)%32`个token，腕部各48个完整保留。前15层KV不变，后10层对齐32。本批T=33–68，实际保留视觉token为258–288，后续前缀为320或352；T=63时本就对齐，完全不裁剪。T=42时保留277个视觉token，前缀331→320。

这里采用VisionZip的注意力评分与上下文合并思路，但压缩发生在ImageWAM多模态前缀内部。保留原始RoPE坐标；合并token采用代表位置与特征均值，未做attention质量补偿，不能视为数学等价操作。

| 模块 | 是否改变及如何解释结果 |
|---|---|
| 图像预处理、VAE、文本编码 | 计算不变；测到耗时下降不能归因于视觉压缩 |
| 多模态前缀 | 后续层序列缩短；包含评分、选择/合并和位置索引开销 |
| 动作专家10轮 | 只减少部分层前缀KV读取；16个动作查询、动作线性层和去噪轮数不变 |

### 为什么native-w4从147.885ms变成176.712ms：基线复核

结论：**两者不是同条件测量。已经确认的配置问题是后续测试主动把MLX内存缓存限制到256MiB，拖慢图像编码；此外，新测试明显存在长尾。未发现native-w4输出或推理数学路径退化。** 之前报告没有突出内存缓存差异，应以本节修正。内存缓存复用GPU分配的缓冲区，不缓存图片特征或推理输出；文本特征缓存是另外一项，所有这些测速均命中。

| 测量 | 配置/输入 | 次数 | 均值ms | 中位数ms | P95 ms |

### 256MiB限制的来源，以及是否影响embody_edge的π0.5

该值是11月9日ImageWAM VisionZip实验新增的资源设置，不是模型要求，也不是MLX强制值。最早的 `screen1/run_experiment.py` 快照没有这两行；后续 `smoke2`、筛选、精度验证和配对性能测试都加入了 `mx.set_cache_limit(256 * 1024**2)` 与 `mx.set_memory_limit(13 * 1024**3)`。其紧邻注释明确说明用途：在另一个MPS评测共享RAM时，限制分配器保留空闲缓冲。随后适配到ImageWAM_MLX时沿用了稳态256MiB/13GiB设置。这个数值未经性能校准，不能因资源控制的意图合理就视为不影响测速；此前没有突出该条件差异是实验设计与报告的问题。

MLX的 `set_cache_limit` 控制已经空闲、供后续复用的内存缓存；超过限额时会在后续分配中回收缓存。它不是文本特征缓存、视觉token数量或KV长度上限。`set_memory_limit`则是图执行的内存使用指导上限，不等于整个进程RSS或系统统一内存的硬性封顶。1GiB也只是本次经过对照的设置，不代表已经证明最优，更不等于完全恢复MLX默认资源策略。

区间为按输入/轮次分组的bootstrap区间。`late_align32`区间跨0，尚不能确认稳定提速。`prune252`均值改善，但P95从189.73升到201.14ms，不能宣称尾延迟也改善。merge252与prune252的直接前缀对照区间跨0，没有证明二者谁稳定更快。8个性能输入包含长度边界和误差较大案例，并非随机抽取的任务分布。

#### 压缩位置和维度

图像拼图按NHWC为 `[1,288,256,3]`，VAE输出 `[1,36,32,32]`，2×2打包为 `[1,18,16,128]`，展平得到288个视觉token，再投影至3072维。文本T个token，加1个状态token，因此未压缩前缀为 `T+1+288`。每层KV形状为 `[1,24,N,128]`；输出仍为16×14，去噪仍为10轮。

| 方案 | 压缩位置 | 视觉token | T=42时各层KV长度 |
|---|---|---|---|
| baseline | 无 | 288 | 25层均331 |
| merge252 | 第5个双流块后 | 240个重要token＋12个上下文代表；252 | 前5层331，后20层295 |
| prune252 | 第5个双流块后 | 直接选择252；三视角168/42/42 | 前5层331，后20层295 |
| prune216 | 第5个双流块后 | 直接选择216；三视角144/36/36 | 前5层331，后20层259 |

merge252的三视角总配额也是168/42/42。保留原位置编码；先前层的完整KV不会追溯压缩。late_align32保留数为 `288-((288+T+1)%32)`，本次覆盖258～288；T=63已经对齐，直接跳过压缩。这是将VisionZip选取/合并思路适配到ImageWAM多模态前缀，压缩发生在VAE之后，因此不减少VAE工作量。

#### 模块与压缩自身开销

独立模块测试使用4个输入，每模块80组配对。缓存中间输入仅用于隔离该模块；以下是独立计时，不能与端到端表相加。

#### 输出偏差与重复稳定性

每方案360个输入/噪声组合，共108帧、36段episode：历史36帧×2个种子，新72帧×4个种子。参考为相同输入和噪声的未压缩native-w4，指标是**归一化动作输出偏差**。

| 方案 | RMSE | episode bootstrap 95%区间 | 最大绝对偏差 |
|---|---:|---:|---:|
| merge252 | 0.003649 | 0.003071～0.004351 | 0.144531 |
| late_align32 | 0.001938 | 0.001852～0.002032 | 0.031250 |
| prune252 | 0.003625 | 0.003130～0.004283 | 0.144531 |
| prune216 | 0.004974 | 0.004403～0.005567 | 0.128906 |

移除allocator限额前后，基线与四个方案各360份action/normalized输出均逐位一致。另在两个独立进程中改变输入组、方案和种子顺序，完成3轮＋2轮共800次重复推理，全部与对应方案参考输出逐位一致。用户要求提高效率后，停止第二进程额外第三轮；原中断记录保留，统计只采用完整完成的两轮，没有报告为960次。

这些结果证明数值可重复及相对基线的离线偏差范围，**不证明任务成功率不下降**。样本元数据来自train，未确认独立留出集；没有闭环机器人成功率测试。RMSE较小也不能忽略局部最大误差，merge252/prune252的最大偏差出现在按蓝色铃铛案例的夹爪输出。

#### 适用范围与选择

稳定指令、文本缓存命中的当前运行条件下，merge252/prune252提供约5%平均降延迟；prune216最快，平均降低10.70%，代价是更高的总体动作偏差。late_align32偏差最小，但提速区间跨0。需要任务级精度保证时，仍需闭环验证后再决定默认开启；当前默认保持关闭。

另测每方案40组冷文本配对，出现秒级长尾。例如merge252配对均值2056.14→999.08ms，但中位数201.11→206.37ms。该组数据完整保留于 `benchmark/results.json` 的 `cold_text`，不能把异常均值差解释成ZIP带来51%加速，也不能将上述热文本148ms泛化到频繁更换指令的场景。服务器共享负载和内存压力是限制因素，现有数据不能严格拆分其因果贡献。

使用现有输入参数，在正式入口追加 `--variant native-w4 --visionzip merge252`；也支持 `late_align32`、`prune252`、`prune216`。不传 `--visionzip` 则不压缩。

完整记录位于 `records/visionzip_default_fresh_20261109/`：`summary.json`、四份 `summary_*.csv`、`stability/`、`allocator_output_comparison.json`，以及各原始测试目录的 `results.json`、源码快照和 `independent_audit.json`。第一次ZIP微测试因编译闭包隐式参数失败，修正为显式传参后通过；失败现场保留在 `zip_cost_failed_attempt1`，推理核心未因此修改。原始数组保留在m5pro，本地同步统计、日志及源码。

正式CLI入口补查通过：`native-w4 + merge252` 的action/normalized与对应验证样本逐位一致，输出元数据正确；不兼容variant和非法preset参数均被拒绝。本次为提高效率只重新运行merge252的正式CLI，其余方案通过模型推理与完整性能/精度测试覆盖。
